# 提交信息规范

这份只管两件事：**哪些文件该进仓库，提交信息怎么写**。工程流程（门禁、发版）在 `版本规则.md`，这里不重复。

## 一、什么进仓库

仓库是公开的（MIT）。进来的东西要满足一条：**别人 clone 下来能跑起来、能贡献、能看懂**。

```text
进仓库                               不进仓库（本地/私有）
├─ engine/        引擎与后端           ├─ dist/            构建产物，每次生成
├─ editor/        编辑器前端           ├─ build/           PyInstaller 中间物
├─ web/           播放器内核           ├─ assets/_generated/
├─ games/         示例作品             ├─ engine/templates/player/   （约 23MB 预构建运行库）
├─ tests/         143 个测试文件       ├─ 审计报告、任务纲领、决策史
├─ tools/         构建与校验脚本       ├─ 尺寸底板探针、临时截图、诊断稿
├─ docs/          用户与贡献者文档     ├─ saves/ *.log .pytest_cache/
├─ brand/ locale/ 品牌与语言           └─ *.apk *.exe *.zip 成品（走 Releases）
├─ android/       安卓壳工程
└─ .github/       流水线
```

三条硬规则：

1. **成品不进库。** APK / exe / zip 只挂 Releases，库里留的是构建脚本。
2. **过程材料不进库。** 审计报告、任务纲领、决策史、探针脚本属于内部记录，留在本地工作区。公开仓只留结论（`docs/` 里的说明与 `CHANGELOG.md`）。
3. **大文件要能说清为什么。** 目前库里三个 >1MB 的：`android/template.apk`（打包模板）、`tools/vendor/uber-apk-signer.jar`（签名器）、`games/newbie_demo/images/林晚_微笑.png`（示例素材）。前两个是构建必须、且不随版本变；第三个是示例作品的画面。新增同类文件前先问一句"能不能换成下载或压缩"。

## 二、提交信息怎么写

格式固定成三段，第一行给人扫，后两段给后来的人查：

```text
<编号> <一句话做了什么>

<为什么>：量到的现象或用户诉求，别写"优化了一下"
<怎么改的>：动了哪一层、边界在哪
<实测>：跑了什么、数字多少（不写"应该没问题"）
```

第一行示例：

```text
P220 手机顶部安全带：刘海/挖孔不再压字，查找改放大镜图标
```

好的：

- `P219 手机端补变量与条件入口：@set / @if 走底部抽屉，写完插到本幕 @end 前`
- `修 countIns 把 @label 算成一句：指令数从 13 掉到 12`

不好的：

- `update`、`fix bug`、`优化界面`、`提交`——三个月后没人知道改了什么、为什么改。
- 一次提交混三件不相干的事。拆开提。

## 三、一次提交的边界

- 一个提交只做一件事；同一件事里"顺手改的格式"可以带上，但要在正文里写一行说明。
- 改 CSS/JS 之后要重新 `python tools/build_editor_single.py`，但**构建产物不进提交**（`dist/` 已在 `.gitignore`）。
- 改版本号、同步 README 徽章、打 tag、发 Release 是一条链，别只做半截（见 `版本规则.md`）。

## 四、提交前自查

```text
[ ] git status 里没有 dist/ build/ 截图 临时文件
[ ] 能说出这次提交"量到了什么现象"
[ ] pytest 跑过，贴了数字
[ ] 动了前端就看一眼手机壳 390 宽
```
