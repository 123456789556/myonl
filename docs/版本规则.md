# 版本规则

> 给用户的一句话：**装最新那个就行，存档不会丢。**
> 不用比版本号，不用记哪个版改了什么 —— 这是这套规则的第一目标。

## 起点

- **v0**：之前的 Python / 早期手机试装版（apk-1 ~ apk-23）。能用，但一直在改，不算正式。
- **v1.0.0**：从 P117 起。手机端第一次能「相册选图 → 进作品 → 出带画面的成品」，
  这条链路通了，才够格叫 v1。

版本号以后就是 `v1.0.0` 这种三段式，**tag 名 = 版本号 = 文件名**，不再另起 `apk-N` 一套。

## 编号：内部 P 号随便跳，对外只在发版时动（P117 起）

- 内部干活用 `P` 号，`P118` 后面直接跳 `P125` 也行 —— 那是我们自己的记账，不用连续。
- `P` 号**不进公开版本线**，也不出现在给用户看的 `CHANGELOG.md` 里。
- 对外**只有真发版**才动版本号。`rc` / `apk` 这类临时标记不再进公开版本线。
- 用户角度看只有一件事：**装最新那个就行**，不用管我们内部跳到第几号。

## 按"更新性质"决定发不发，不按时间

判据只有一条：**用户装完之后，有没有感觉到不一样？**

| 档 | 性质 | 判据（问自己） | 版号动作 | 节奏 |
|---|---|---|---|---|
| **A 能力** | 以前做不到的事，现在能做了 | 装上之后能编出以前编不出的东西？ | `v1.0.0 → v1.1.0` | 做完就发，一两个月一次 |
| **B 表现** | 看得见的地方变了 | 界面、布局、横竖屏、操作步骤明显不同？ | 末位 +1：`v1.1.0 → v1.1.1` | 攒，够三处一起发 |
| **C 修正** | 修掉影响使用的问题 | 不修就有人用不下去？（点了没反应、存档丢、文件导不出） | 末位 +1 | 影响使用立刻发，否则攒 |
| **D 内部** | 外面完全看不出来 | 重构、注释、测试、构建脚本、调像素 | **不动版号** | 只提交 |

**末位就是给"小改动"留的**：B 和 C 都只动最后一位，不跳次版本。
`v1.0.1` 这种号意味着"装机之后你会发现某处不一样，但没有新增一项能力"。

D 类是绝大多数改动。**只提交、不发版**是常态，不是偷懒。

反向清单（这些一律算 D，别为它们发版）：

- 改注释、改变量名、拆函数
- 补测试、改文档、改 CI
- 一两个像素的间距、颜色微调
- `_tools/` 下的验收脚本
- 折腾半天又回到原样
- **只改了 README / 版本说明本身**

## 发版就写日志，不写日志就等于没发

每次打 tag 之前，`docs/CHANGELOG.md` 顶部必须有一节，写的不是"改了哪些文件"，而是：

1. **用户能感觉到什么变了** —— 一句话，用他能听懂的话（"手机能把图放进作品了"，不是"新增 IndexedDB 素材层"）。
2. **为什么以前不行** —— 一句，让人知道这不是可有可无的装饰。
3. **验收数字** —— 几条几通过，怎么验的。数字要能复跑，不能凭印象。
4. **已知上限** —— 这版还做不到什么，直接说。

不写这四条就打 tag，等于把"用户能不能感知"的活留给下载的人自己猜 —— 那是最贵的认知负担。

## 文档口径：后面的覆盖前面的

仓库里的 md 只会越写越多，早期那些迟早和磁盘对不上。**判先后只看一件事：哪份更接近现在的磁盘和 CI。**

顺序（上 > 下）：

| 优先级 | 文件 | 管什么 |
|---|---|---|
| 1 | `README.md` | 现在这个产品是什么、装哪个包、手机上能干什么 |
| 2 | `docs/CHANGELOG.md` 最新一节 + 本文件「版号对照」 | 最近一版到底改了什么、验收数字 |
| 3 | `docs/版本规则.md`（本文件） | 怎么发版、什么算 A/B/C/D 档 |
| 4 | `docs/快速上手.md`、`docs/mobile/手机端编游戏.md`、`docs/desktop/打包使用指南.md`、`docs/素材导入指南.md` | 具体操作步骤 |
| 5 | `docs/engine_spec.md`、`docs/架构说明.md` | 现行权威参考：指令全集 / 代码结构 |
| 6 | `docs/产品说明书.md` | 设计取舍与历史原因，追"为什么这么定"时看 |

- **冲突时以后写的为准**，前面的当场改掉或加上过时横幅。不许两份并存、让读者自己挑。
- **方向变了就先改 md 再改代码**：md 里新写的那条，就是下一步要干的活；反过来（代码先变、md 后补）最容易半途漂走。
- 数字（测试数、体积、下载数）一律带日期和口径，能复跑才写；凭印象写的一律当没写。
- 文档和磁盘不一致，按项目规矩**当场改文档并登记**，不许只记不改。

## 一条硬规矩：升级不能丢档

比版本号重要得多。任何一次发版，装过旧版的人升级后**本地作品和素材必须还在**：

- **签名不变**（`android/keystore/`），安卓才允许覆盖安装，不清数据；
- **存储键带版本**（`myonl:v2:*`、`myonl:assets:index:v1`），新版只读旧键、不删；
- **要改结构就写迁移**：读到旧格式就地转新格式再存回去，绝不新开一个空库。

版本号错了只是难看；存档没了是事故。这条永不妥协。

## 发版流程（照这个顺序，不跳步）

```
py -3 -m pytest -q                     # 全绿才继续
py -3 tools/build_editor_single.py     # 重建单文件
git commit / push                      # 先上主干
git tag -a v1.1.0 && git push tag      # 打 tag，CI 出包
等 CI 出包 → 改 README 徽章与下载链 → 再 commit
```

- 徽章的版本号与下载链接**必须一致**（`tests/test_p106_release_hygiene.py` 守着）。
- Releases **只留最近 3 个**，`tools/gh_release_clean.py --prune` 清旧的。
  别人只认"最新那个"，历史堆着没用。
- **versionCode**：tag 发版走语义码 `MAJ*10000 + MIN*100 + PAT`；手动触发（workflow_dispatch）
  或分支构建不是发版，用单调递增的 CI 运行号当 versionCode（版本名 `0.0.0-dev.<运行号>`），
  不再恒为 1，覆盖安装能分出新旧。

## 大素材（几百 MB ~ 几 GB）怎么说

手机**存得下**：素材压在 IndexedDB 里，配额跟着磁盘走，几百 MB 到几 GB 都能放。

**但导出方式要分两条路**，这是必须让用户知道的一个边界：

| 素材总量 | 导出方式 | 说明 |
|---|---|---|
| 小（导出后约 40MB 以内） | **单文件 .html** | 图内联成 base64 塞进 HTML，一个文件发给谁都能开。这是现在支持的路。 |
| 中（40MB ~ 80MB） | 单文件强提示，不硬拦 | 40MB 起软提醒；80MB 硬线做强提示（仍可导出），但低端机大概率白屏或闪退。 |
| 大（80MB 以上） | 文件夹 / zip | 图放旁边，HTML 引用它们。**还没做**。 |

为什么现在不能硬撑：base64 会让体积涨三分之一，几百 MB 的 HTML 光解析就能把手机浏览器卡死。
硬做等于给人一个打不开的文件，比不支持更糟。所以这条路留到有正经的"发行包"再开。
