# 贡献指南（给改代码的人）

> 目标：任何人拿到仓库，能在 **不读完整代码** 的情况下跑起来、改一处、验证并提交。
> 结构看 [架构说明.md](架构说明.md)，语法看 [engine_spec.md](engine_spec.md)。

## 一、环境

- 开发机：Windows 10/11（当前实际只在 Windows 上开发过；引擎本身不依赖 Windows 特有 API）
- 产物不是「Windows 专属」：主出口是**安卓 APK**（手机一台就能编、能玩），
  以及**单文件 HTML**（任何浏览器双击即开）。桌面 Python 引擎用来在电脑上跑同一批剧本
- Python 3.9 或更高（CI 矩阵覆盖 3.9–3.15，见 `.github/workflows/tests.yml`；本机 `py -3 --version` 确认）
- 安装依赖：`py -3 -m pip install -r requirements.txt`
- 不需要 Node / 打包工具：前端是原生 HTML/CSS/JS，无构建步骤

## 二、跑起来

```powershell
# 跑示例（无窗口截图验证用 --max-frames）
py -3 -m engine.demo games/标准示例/script.gal --assets games/标准示例

# 打开编辑器（浏览器模式）
py -3 -m engine.editor --project games/标准示例

# 命令行新建工程
py -3 -m engine.cli new 我的游戏
```

## 三、提交前必须跑的门禁

| 命令 | 作用 | 通过标准 |
|---|---|---|
| `py -3 -m pytest -q` | 全量测试 | 0 failed（允许已知 skip） |
| `powershell -File tools/check_types.ps1` | pyright 棘轮 | 无新增类型错误 |
| `powershell -File tools/check_coverage.ps1` | 覆盖率 | `engine/` ≥80% |
| `powershell -File tools/preflight.ps1 -Fast` | 一键门禁（pytest + pyright 等） | exit 0 |
| `py -3 tools/build_release_zip.py --verify` | 发行包（改了打包/前端时） | 解压冒烟通过 |

只跑相关测试做快速迭代可以，但**提交前至少跑一遍 `preflight.ps1 -Fast`**。

## 四、代码约定

- 注释与文档用中文；提交信息用中文。
- 渲染模块按 Mixin 拆分：新效果放新的 `engine/render_xxx.py`，在 `renderer.py` 组合；单文件 ≤700 行。
- `editor/index.html` 保持 <600 行；交互逻辑放对应 `editor_*.js`，不要往 HTML 里堆脚本。
- 不引入打包器/框架/新依赖，除非有明确理由并同步 `requirements.txt` 与 `NOTICE`。
- 解析器不做文件 I/O 之外的事；运行时只产出事件，不直接绘制。
- 玩家侧可配置项走 `config.json`（项目）→ `settings.json`（玩家）三层覆盖，不要写死。

## 五、改一处，要同步哪些地方

| 你改了什么 | 必须同步 |
|---|---|
| 新增/修改剧本指令 | `engine/parser.py`、`engine/runtime.py`（如涉及执行）、`docs/engine_spec.md` §2、`tests/test_parser.py`、编辑器补全/高亮（如需要） |
| 新增 UI 配置键 | `engine/config.py` 默认值、`docs/engine_spec.md` 配置表、UI 设计区（如适用）、测试默认值断言 |
| 新增素材 | 直接放 `engine/templates/standard/images`（内置素材）或走 `tools/import_assets.py`（批量导入）、补 `tests/test_builtin_assets.py` |
| 改打包流程 | `pack.py` / `engine/packaging.py`、`tools/build_release_zip.py`、`docs/打包使用指南.md` |
| 改前端交互 | 对应 `editor_*.js` + `editor.css`、`tests/test_u_interactions.py` 或 `test_code_health.py` 的结构断言 |

## 六、提交信息

格式：`类型(范围): 一句话说清为什么`

```
feat(parser): 支持 @[角色] 方括号台词
fix(editor): 场景页遇 BOM 时误报没有场景
docs(spec): 同步指令表与新台词语法
test(ui): 补图层顺序面板守护
chore(release): 同步发行版构建与打包配置
```

- 一次提交只做一件事；不要混入无关格式化。
- 不提交 `dist/`、`build/`、`__pycache__`、存档、临时 `tmp*.gal`。

## 七、文档纪律

- 版本号以仓库标签与 README 为准；不要在正文手写过时的测试数/覆盖率数字。
- 承载现行口径的文档必须与当前版本一致：`README.md`、`docs/快速上手.md`、`docs/架构说明.md`；
  `docs/开发者使用指南.md` 只做导航指路，不承载版本内容，改语法/模板/新建流程时不用同步它。

## 八、PR / 交付检查清单

- [ ] 功能可运行，且说明了怎么验证（命令或截图）
- [ ] 相关测试已加/已改，全量 `pytest` 通过
- [ ] `check_types.ps1`、`check_coverage.ps1` 通过
- [ ] 文档已同步（语法/配置/模板/版本）
- [ ] 没有提交生成物、临时文件、密钥

## 九、本地先落盘，再上 GitHub（2026-11-19 立）

一句话：**改动先进本机的 git，再推远端。不许「改完直接推」。**

为什么不是形式主义：

- 推上去的是**公开历史**。写错、推错，force push 只改得动 ref 和我的那份，
  改不掉别人已经 clone 的副本。
- 本机的一次 commit 就是一个免费撤销点；**没 commit 的改动没有撤销点**，
  一次误操作、一次环境被切走，就没了。
- 2026-11-19 的真实教训：签名 secret 被清空 + 代码编译不过，两件事叠在一起，
  当时没有人能立刻回答「上一个好的版本是哪一版」——因为中间没有落点。

具体步骤，每条都是踩过坑才写的：

1. **动笔前先看工作树**：`git status`。
   树不干净说明有半成品，先弄清楚是谁的。同一文件同期只允许一个写手。
2. **改完先 commit，不是先 push**。提交信息写「为什么」，不写「优化」「优化一下」。
3. **提交前跑门禁**：至少 `py -3 -m pytest -q`。报绿必须给**退出码和实测数字**，
   不能转述别人跑的结果。
4. **push 前先 `git fetch`**，确认没落后；落后先合，不许硬推。
5. **一次提交只做一件事**。混在一起的提交，回退时会连累无辜改动。
6. **公开仓和本地待定区分开**：陌生人 clone 下来能跑能懂的东西才进公开仓；
   别人的作品/素材、半成品、内部笔记留在**本地待定区**，不推公开仓。
   拿不准的一律不进公开仓——推上去就是再分发，收不回来。
7. **文档和磁盘不一致时当场改**，不许只记不改。
   文档里的测试数、覆盖率、包体积一律当**未证实声明**，引用前重跑或标注「未复跑」。
8. **发版另算**：内部 `P` 号随便跳；对外 `v` 号只在真正发版时动（见 [版本规则.md](版本规则.md)）。
   tag 一旦推过又必须改，要在 CHANGELOG 里写清「为什么移了 tag」，不许悄悄改。

> 这条规则的边界：它是**保护你自己的回退能力**，不是审批流程。
> 本机提交随时可以做；只有「推公开仓」和「发版动 tag」才需要想清楚。
